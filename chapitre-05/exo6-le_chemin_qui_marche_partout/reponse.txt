Ce qui a change : entre les deux lancements, ni le code ni le fichier de texture n'ont changé : c'est le même exécutable qui a tourné deux fois. La seule différence est le dossier courant, celui d'où le programme est lancé. Lancé depuis C:\Dev\Nkentseu, le chemin relatif murs/mur.jpeg part de ce dossier, y trouve le fichier, et le mur est texturé. Lancé depuis C:\Dev\Nkentseu\Build\Bin\Debug-Windows\ExoChemin, il part de ce dossier-là, n'y trouve rien : le moteur remplace la texture par du magenta et écrit une erreur dans le journal. Ce n'est donc pas le code de rendu qui est en cause, c'est le dossier courant. Avec LocateResource, les deux lancements affichent la texture.

Ce que LocateResource essaie : d'après le commentaire de NkPath.h, elle cherche dans cet ordre : 1. le dossier courant ; 2. le dossier de l'exécutable ; 3. les parents de l'exécutable, 8 niveaux au plus ; 4. les parents du dossier courant, 8 niveaux au plus. Dans chaque dossier, toutes les variantes données sont essayées avant de passer au dossier suivant, et un chemin absolu qui existe est rendu tel quel. Elle rend le chemin absolu trouvé, ou une chaîne vide si rien n'existe ; avec warnIfMissing à true, elle écrit alors au journal un avertissement qui liste les dossiers essayés. Dans mes essais : depuis le projet, elle trouve murs/mur.jpeg dès la première étape ; depuis Build, ni le dossier courant ni celui de l'exécutable n'ont de dossier murs, elle trouve le fichier en remontant les parents de l'exécutable, la racine C:/Dev/Nkentseu étant 4 niveaux au-dessus. Comme le résultat peut être vide, mon code le teste avant de le donner à Load.
